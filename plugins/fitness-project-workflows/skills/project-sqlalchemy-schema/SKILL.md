# Project SQLAlchemy schema workflow

Read the applicable application `AGENTS.md`, `migrations/AGENTS.md`, and the current project-state handoff before proposing or making a schema change. Preserve the user's authorized scope and never access `.env` values.

## Design and migration

- Use SQLAlchemy 2.x typed declarative mappings: `Mapped[...]`, `mapped_column(...)`, and relationships with explicit `back_populates`.
- Prefer references to classes or columns over raw strings where doing so does not create an import cycle. Model an association table with domain data as an association object, never also as a `secondary` relationship over the same table.
- Make the model change and generate an Alembic revision only after the desired schema is clear. Autogenerated revisions are candidates, not accepted output.
- Review the revision's table and constraint names, nullability, defaults, indexes, foreign keys, upgrade operations, and downgrade operations. Remove unrelated operations.
- Do not apply a schema-changing command without the user's authorization. Do not use runtime DDL or `db.create_all()`.

## Tests and handoff

- Add or update migration-backed tests through the project pytest workflow when the change affects database behavior.
- Run the relevant configured checks and report the actual migration verification state. If configuration is required, give the user a non-secret local command and expected result.
